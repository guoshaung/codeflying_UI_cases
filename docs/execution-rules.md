# 执行规则

## 基础原则

1. 用户明确指定的 suite / case 高于历史固定用例。
2. 登录可以作为前置条件；如果本次不测试登录，不应把登录计入用例总数。
3. 失败、阻塞、未执行不得计入通过数。
4. 工具错误经重试恢复后，状态记为 `RETRY_PASS`，并保留首次错误证据。
5. HTTP 200 不等于业务成功，必须检查页面结果、业务码和关键数据。

## 依赖应用的用例

涉及下载源码、助手配置、发布、预览、改名、发布列表时，必须先取得稳定可用的测试应用：

1. 优先从“我的应用”选择已有应用。
2. 不选择正在转圈、生成中、构建中、处理中或状态不稳定的应用。
3. 需要确认当前账号拥有该应用，并且能看到所有者入口。
4. 如果没有可用应用，可从公开应用卡片“做同款/复制”得到副本。
5. 如果两条路径都失败，依赖用例标记为 `BLOCKED`，独立用例继续执行。

## 支付用例

支付测试需要拆分：

- 二维码生成：可自动化。
- 测试支付回调 / 支付沙箱：有沙箱或 mock 时可自动化。
- 真实扫码支付：默认真人依赖。

没有支付沙箱时，不应把“二维码生成成功”写成“支付成功”。
