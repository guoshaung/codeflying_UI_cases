# CodeFlying 10 条稳健测评用例

> 版本：v1.4  
> 日期：2026-07-15  
> 测试环境：<https://dev.codeflying.net/>  
> 用例来源：`full-test-runner/references/CodeFlying_case_from_wz.md`  
> 用途：CodeFlying Web 自动化测试 Agent 的核心能力验收与回归测评

## 1. 测评目标

本测评集包含 10 条核心用例，覆盖简易自然语言交互、应用下载、助手配置、微信小程序发布、应用预览、应用管理、测试支付和应用卡片在线体验。

登录操作仅作为统一前置条件，不计入 10 条测评用例。测试必须真实执行并保留证据；未执行、证据不足或依赖无法完成时，必须如实标记为阻塞或失败。

## 3. 全局执行规则

1. 10 条用例必须在同一次测试任务中执行，并保持同一个 `test_seq`。
2. 可以内部按批次组织工具调用，但批次之间不得暂停等待用户回复“继续”。
3. 10 条用例均依赖真实登录态；登录仅为前置条件，不计入用例数量和通过率。
4. TC-001-LITE 只验证助手返回首条有效回复，不负责生成后续用例使用的应用，也不得把它的 PASS 当作“应用创建成功”。
5. 执行依赖应用的用例前，必须先完成“测试应用解析”，取得当前账号拥有且允许测试的 `resolved_app`；不得因“我的应用”暂时为空就直接阻塞全部依赖用例。
6. TC-002 发布成功后，TC-003 必须复用同一个 `resolved_app` 验证发布结果是否落入“已发布”列表。
7. TC-620 不仅要验证跳转动作，还要验证帮助与支持页面成功加载并展示主要帮助选项。
8. 二维码“可识别”必须同时满足：资源加载成功、图片无破损、二维码解码结果非空；仅肉眼可见不算通过。
9. 下载“正常”必须验证下载事件触发、文件实际落盘、文件大小大于 0，并检查文件类型或压缩包可读性。
10. 工具返回 `Error`、`Timeout`、`not found`、`strict mode violation` 或业务接口失败时，不得直接判定通过。
11. 工具错误经重试恢复后，状态应记录为 `RETRY_PASS`，同时保留首次错误证据。
12. HTTP 200 只代表请求到达服务端；必须继续检查业务码、响应数据和页面结果。
13. 页面元素“可见”不等于功能完成，必须验证用例规定的最终业务结果。
14. 失败、阻塞和未执行用例不得计入通过数。
15. 任何 P0 用例失败或阻塞时，不得输出“全部通过”“100 分”或“建议上线”。

## 4. 登录与测试数据前置条件

在执行 10 条用例前，在主测试上下文中加载 `login-automation-test`，严格执行：

1. 输入由安全环境变量提供的测试手机号 11451419198；
2. 点击“获取验证码”并完成滑块验证；
3. 确认验证码发送接口业务成功；
4. 使用 `get_redis_code.py` 从 Redis 读取本次验证码，Redis 端口为 `6279`；
5. 填写验证码并点击登录；
6. 检查登录接口业务响应成功；
7. 验证页面离开登录页；
8. 验证当前用户接口返回有效用户信息；
9. 验证至少一个登录后受保护页面可访问。

同时准备一个可用于“在线体验”的公开应用卡片，以及测试会员套餐和可控的测试支付环境。测试手机号、Redis 密码和其他敏感凭据不得写入仓库。

### 测试应用解析

该过程是测试数据前置步骤，不计入 10 条 Case。必须按顺序执行：

1. 进入“我的应用”并扫描应用卡片。排除任何仍显示转圈加载动画、骨架屏、“生成中”“构建中”“处理中”“等待中”或类似未完成状态的应用。
2. 仅从状态稳定、没有转圈且明确可用于自动化的应用中选择候选；优先选择名称带测试标识、最近完成且不会影响生产数据的应用。
3. 打开候选详情，确认页面停止加载、主要内容正常显示，并验证当前账号拥有下载、配置、发布、预览和改名入口；全部成立后记录为 `resolved_app`。
4. 如“我的应用”为空、所有应用都在转圈或没有安全可用的候选，进入浏览应用页，复用 TC-111 选中的公开应用卡片，打开“在线体验”并点击“做同款”或等价复制入口。
5. 等待副本创建完成；只有副本卡片停止转圈、不再显示生成/构建状态、详情页正常打开且所需操作入口可用时，才将其记录为 `resolved_app`。持续转圈的副本不得选用。
6. 记录 `resolved_app` 的来源（`existing` 或 `clone`）、原始应用名称、当前名称、应用 ID、详情链接、稳定状态证据和是否需要清理。
7. 只有“无转圈的已有应用”和“做同款/复制后完成的副本”两条路径都真实尝试失败后，才允许将 TC-009-MENU、TC-006、TC-002、TC-004、TC-210 和 TC-003 标记为 `BLOCKED`。
8. 测试应用解析失败不得中止 TC-111、TC-603 和 TC-620；这些独立用例必须继续执行。
9. 若本次创建了副本，所有依赖用例和证据采集完成后再删除副本；清理失败必须写入报告。

### `resolved_app_ready` 强制门禁

取得 `resolved_app` 后，还必须完成以下检查，全部成立才能开始 TC-009-MENU、TC-006、TC-002、TC-004 等依赖完整应用的用例：

1. 进入完整应用页 `/to-app?app_id={resolved_app.app_id}`，不得仅停留在应用开发过程页 `/application`；若当前在 `/application`，必须通过预览、打开应用或等价入口进入 `/to-app`。
2. 当前 URL 中的 `app_id` 必须与 `resolved_app.app_id` 一致，页面显示的应用名称也必须与 `resolved_app` 一致。
3. 等待页面加载、骨架屏及生成/构建状态结束，确认主要内容正常显示。
4. 确认当前账号是该应用所有者：应能看到“发布”“下载源码”等所有者入口；若页面显示“做同款”“复刻”或其他访客入口，则该应用不满足条件，必须重新解析测试应用。
5. 记录当前 URL、应用 ID、应用名称、所有者状态和完整应用页截图，作为 `resolved_app_ready` 证据。
6. 门禁未通过时必须重新尝试已有应用或做同款/复制路径；不得直接开始依赖用例，也不得据此断言“下载源码”“助手配置”或“发布”等产品入口不存在。

结果判定必须区分：无法进入正确的完整应用页或无法确认所有者状态，标记为前置条件 `BLOCKED`；已进入当前账号拥有且加载完成的 `/to-app` 页面，但目标入口确实不存在，才判定对应产品用例 `FAIL`。

不得使用不属于当前账号的公开应用直接执行发布、改名或其他写操作。不得选择名称或标签表明是生产用途的应用。不得为了继续测试而选择仍在转圈或状态未完成的应用。

## 6. 详细测评用例

### TC-001-LITE 正常创建应用－简易版

- 模块：创建应用
- 前置条件：真实登录态验证成功。
- 测试输入：一段简单、明确的自然语言，例如“创建一个待办事项应用”。
- 测试步骤：
  1. 进入创建应用页面；
  2. 输入简单自然语言需求；
  3. 提交需求；
  4. 等待助手返回首条有效回复。
- 预期结果：助手成功接收需求并返回与输入相关的非空回复，不要求等待完整应用生成。
- 通过证据：提交前后的输入内容、助手回复、相关业务接口结果和页面快照。
- 失败条件：提交无响应、回复为空、回复与输入明显无关、接口报错或持续加载超时。
- 特别说明：收到首条有效回复后即可结束本用例；后续应用是否完成生成不属于本用例判定范围。不得仅凭后续未继续响应就断言 AI 生成后端未启动，也不得把本用例输出当作 `resolved_app`。

### TC-009-MENU 下载源码

- 模块：创建应用
- 前置条件：真实登录态验证成功，测试应用解析成功并取得 `resolved_app`，且 `resolved_app_ready` 强制门禁已通过。
- 测试步骤：
  1. 打开 `/to-app?app_id={resolved_app.app_id}`；
  2. 验证 URL 中的 `app_id`、页面应用名称及当前账号所有者状态；
  3. 验证完整应用页头部或右上角存在“下载源码”入口；
  4. 点击“下载源码”入口；
  5. 等待浏览器产生真实下载并等待下载任务完成；
  6. 检查下载文件的文件名、类型、大小且文件非空。
- 预期结果：“下载源码”入口可点击，并成功下载对应文件。
- 通过证据：`resolved_app_ready` 页面截图、URL 与应用信息、所有者状态、“下载源码”入口及点击事件、浏览器下载记录、落盘文件路径、文件名、大小及文件类型。
- 失败条件：已通过 `resolved_app_ready` 门禁但下载入口不存在、下载未触发、文件为空或文件损坏。未通过门禁时必须标记前置条件 `BLOCKED`，不得报告为产品“下载按钮缺失”。

### TC-006 助手配置显示二维码

- 模块：经营助手
- 前置条件：真实登录态验证成功，测试应用解析成功并取得 `resolved_app`。
- 测试步骤：
  1. 进入 `resolved_app` 页面；
  3. 点击“助手配置”；
  4. 点击企业微信客服“配置”；
  5. 等待 10s 左右检查并识别弹出的二维码。
- 预期结果：配置界面正常弹出，二维码加载成功、无破图且解码结果非空。
- 通过证据：操作路径、配置弹窗、二维码资源状态、二维码尺寸和解码结果。
- 失败条件：入口不可用、配置界面未弹出、二维码破图或二维码无法识别。

### TC-002 微信小程序发布版本及二维码

- 模块：发布应用
- 前置条件：真实登录态验证成功，测试应用解析成功，`resolved_app` 具备发布条件。
- 测试步骤：
  1. 进入 `resolved_app` 页面；
  2. 点击右上角“发布”；
  3. 点击“微信小程序发布”；
  4. 进入发布版本选择页面；
  5. 选择“快速体验版”，触发发布并检查二维码；
  6. 返回版本选择，选择“正式版”，触发发布并检查二维码；
  7. 记录两种版本的发布状态和二维码识别结果。
- 预期结果：可以分别选择快速体验版和正式版；两种发布流程均能生成加载正常、无破图且可识别的二维码。
- 通过证据：版本选择状态、二维码资源状态及解码结果。
- 失败条件：二维码未生成、二维码破图或无法识别。

### TC-004 应用界面启动预览

- 模块：创建应用
- 前置条件：真实登录态验证成功，测试应用解析成功并取得 `resolved_app`。
- 测试步骤：
  1. 进入 `resolved_app` 页面；
  2. 点击“应用界面”；
  3. 启动应用预览；
  4. 等待预览区域加载完成；
  5. 检查主要界面和至少一个基础交互。
- 预期结果：应用预览成功启动，iframe 或预览区域正常加载，无白屏、无阻断性报错，基础交互可用。
- 通过证据：预览启动动作、加载完成状态、预览界面快照、控制台错误和关键接口结果。
- 失败条件：无法进入应用界面、预览无法启动、白屏、加载超时或关键交互不可用。

### TC-210 修改应用名称

- 模块：我的应用
- 前置条件：真实登录态验证成功，测试应用解析成功并取得允许改名的 `resolved_app`。
- 测试步骤：
  1. 进入“我的应用”；
  2. 记录应用原名称；
  3. 打开应用卡片右下角三点菜单；
  4. 选择“修改名称”；
  5. 修改为带本次时间戳的唯一测试名称并保存；
  6. 刷新页面，验证新名称仍然存在；
  7. 测试完成后恢复原名称并再次刷新验证。
- 预期结果：名称修改成功、列表同步、刷新后保持；清理阶段成功恢复原名称。
- 通过证据：原名称、新名称、保存接口结果、刷新后状态和恢复结果。
- 失败条件：保存失败、列表不同步、刷新后丢失或无法恢复原名称。

### TC-603 购买积分－支付二维码生成

- 模块：我的权益
- 前置条件：真实登录态验证成功，“我的权益”页面可访问；测试支付环境、mock 支付或微信支付测试配置至少有一项可用。
- 测试步骤：
  1. 进入“我的权益”页面；
  2. 检查当前账号会员状态；如果账号已经是会员，不得直接阻塞；
  3. 向下滚动页面，查找“购买积分”或等价积分套餐区域；
  4. 选择任意可购买的积分套餐；
  5. 点击“购买”或等价确认按钮；
  6. 检查是否弹出支付二维码；
  7. 检查二维码资源加载状态、图片尺寸、是否破图，并尽量完成二维码识别；
  8. 如果“微信支付测试”已开启，检查支付金额是否为测试金额（例如 0.01）；
  9. 如果 mock 支付已开启且页面或接口提供 mock 支付完成能力，则触发 mock 支付，并验证积分余额、订单状态或权益接口更新；
  10. 如果仅完成二维码生成，必须在报告中写明“支付二维码生成成功”，不得写成“支付成功”。
- 预期结果：购买积分入口可见；点击购买后弹出有效且可识别的支付二维码；测试支付金额符合环境配置。mock 支付可用时，支付完成后积分或订单状态正确更新。
- 通过证据：当前会员状态、购买积分入口、套餐信息、支付金额、二维码资源状态、二维码尺寸和识别结果；如执行 mock 支付，还需记录 mock 支付回调、订单状态和积分余额变化。
- 失败条件：我的权益页面无法访问、购买积分入口缺失、套餐不可点击、二维码未弹出、二维码破图或二维码无法识别；mock 支付已开启但支付成功后积分/订单状态未更新。
- 阻塞条件：支付配置未开启、没有可购买的积分套餐、二维码依赖第三方真实扫码且本轮无人工辅助、mock 支付入口或接口不可用。
- 特别说明：已是会员不等于不可测试支付；应继续测试“购买积分”链路。没有完成真实扫码或 mock 支付时，只能判定“二维码生成成功”，不得判定“支付成功”。

### TC-111 应用卡片在线体验

- 模块：浏览应用
- 前置条件：真实登录态验证成功，“最新”应用列表中存在可体验应用。
- 测试步骤：
  1. 进入浏览应用页面；
  2. 切换至“最新”；
  3. 将鼠标悬浮在应用卡片上；
  4. 点击“在线体验”；
  5. 等待体验窗口加载；
  6. 检查应用主要界面；
  7. 关闭体验窗口。
- 预期结果：在线体验入口可用，体验窗口正常打开并展示应用完整界面，关闭后无残留遮罩。
- 通过证据：悬浮状态、在线体验点击、体验窗口、应用界面加载结果和关闭结果。
- 失败条件：入口不可见或不可点击、窗口未打开、预览白屏、加载报错或窗口无法关闭。
- 输出变量：记录本次体验的公开应用名称、卡片或详情链接；测试应用解析需要克隆时优先复用该候选。

### TC-003 发布后应用列表展示

- 模块：我的应用
- 前置条件：TC-002 发布成功，复用同一个应用。
- 测试步骤：
  1. 进入“我的应用”；
  2. 点击“已发布”标签；

## 7. 状态定义

| 状态 | 判定标准 |
|---|---|
| PASS | 全部规定步骤完成，预期业务结果成立，证据充分。 |
| RETRY_PASS | 首次执行出现工具或定位错误，重试后完整验证通过；必须保留首次错误。 |
| FAIL | 已执行但实际业务结果不符合预期，或发现真实产品缺陷。 |
| BLOCKED | 因登录、测试数据、环境、权限、依赖或工具能力无法完成验证。 |
| NOT_RUN | 未执行，不得计入通过数。 |

## 8. 报告要求

最终报告必须包含：

1. 测试地址、时间、浏览器、测试序号和 Agent 版本；
2. 10 条用例逐条结果及状态；
3. 每条用例的关键工具调用、业务接口和页面证据；
4. 登录自动化全过程证据；
5. 首次工具错误、重试动作和重试结果；
6. 测试应用解析的两条路径、被排除的转圈应用、`resolved_app` 来源、名称、ID、详情链接、稳定状态证据和副本清理结果；
7. TC-002 与 TC-003 的应用依赖关系；
8. TC-210 的原名称、测试名称和恢复结果；
9. 所有二维码的资源状态和解码结果；
10. TC-620 点击前后的 URL、页面标题和主要帮助选项；
11. PASS、RETRY_PASS、FAIL、BLOCKED、NOT_RUN 分项统计；
12. 每个状态必须列出对应的唯一用例 ID，表格数量必须等于所列 ID 数量；
13. 所有问题按严重程度归类，并明确给出是否建议继续回归或上线。

状态统计必须从 10 条逐条结果机械汇总，不得手工填写互相矛盾的数字。例如列出 3 个通过用例时，通过数必须为 3，通过率必须为 30%，不能写成“通过 2、通过率 20%”。`RETRY_PASS` 单独展示，并在计算通过率时明确是否计入通过。

报告必须满足数量守恒：

```text
总用例数 = PASS + RETRY_PASS + FAIL + BLOCKED + NOT_RUN = 10
```

以下任一情况出现时，报告不得给出满分或建议上线：

- 登录前置条件失败或阻塞；
- 任何工具 Error 未解释；
- 任何 P0 用例失败或阻塞；
- 用例执行证据不足；
- TC-210 未完成数据恢复；
- 二维码仅显示但未完成识别验证；
- 下载仅触发但未验证落盘文件。
